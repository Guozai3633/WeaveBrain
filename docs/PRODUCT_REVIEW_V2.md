# 织脑（WeaveBrain）产品重定向评审 V2

> 状态：评审草案  
> 日期：2026-08-16  
> 目的：重新对齐原始用户问题、产品目标与当前实现；旧 PRD 暂不覆盖，待 V2 评审通过后再替换。

## 1. 管理层结论

织脑解决的是真实问题，但当前项目更像“AI 技术能力集合”，还不是一个用户可以信任的产品。

原始需求的本质不是多 Agent、MCP 或自动执行，而是：

> 当用户在跑步、散步、通勤等不方便深入工作的时刻突然产生想法，能够几乎不打断当下状态地把它可靠保存；系统随后替用户整理、关联、追问和再次带回，让想法不丢失、可理解、能继续生长。

因此 V2 的最高原则是：

> **先确保每个想法被安全捕捉，再让 AI 异步理解它。**

当前阶段应定义为“技术原型 / Pre-MVP”，而不是“11 个 Sprint 已完成的 MVP”。项目不需要推倒全部代码，但需要推翻现有核心编排和功能优先级。

## 2. 产品定位

### 2.1 一句话定位

**织脑是一款面向高频思考者的情境化灵感记忆工具，让用户在运动和碎片场景中无屏捕捉想法，并由 AI 在合适的时间重新整理、关联和带回。**

### 2.2 用户要雇佣它完成的工作（JTBD）

当我在跑步、散步、通勤或临睡前突然产生一个值得保留的想法时，我希望不用停下来组织语言或管理分类，就能立刻把它安全记下；等我有精力时，系统已经帮我还原重点、保存当时情境、关联旧想法，并给出一个轻量的继续入口。

### 2.3 首批核心用户

不是泛化的“专业人士和学生”，而是满足以下特征的人：

- 中文为主要表达语言；
- 每周至少产生 3 次需要临时记录的灵感；
- 经常在步行、跑步、通勤、家务或睡前进行发散思考；
- 当前使用微信收藏、系统备忘录、录音机或给自己发消息，但事后很少整理；
- 愿意为了“不丢想法”和“旧想法被重新激活”持续使用产品。

优先邀请独立开发者、产品经理、设计师、内容创作者、研究者等高频创造型用户参与内测。

### 2.4 暂不服务的人群

- 以多人会议转写为主要诉求的团队；
- 需要完整项目管理、任务协作或 CRM 的企业用户；
- 仅偶尔使用一次语音转文字的低频用户；
- 需要把所有操作交给自动 Agent 执行的高级自动化用户。

## 3. 差异化判断

“语音记录 + AI 摘要 + 标签 + 知识库 + MCP”已经是成熟品类能力，不能作为上市差异化。

织脑应围绕以下组合形成产品楔子：

1. **运动/独处场景的低摩擦捕捉**：尽可能无屏，启动快，有声音或触觉确认。
2. **零丢失承诺**：先本地保存，断网可用，后台可重试，AI 故障不影响记录。
3. **情境记忆**：在用户授权下保留时间、时区、入口、设备和可选的地点/活动线索。
4. **分阶段输出**：当下只确认保存；稍后生成整理卡；隔天或隔周再关联旧想法，不在录音结束后一次性轰炸用户。
5. **主动但克制的复现**：不是无限推送，而是在用户可控制的频率下，把真正相关的旧想法带回来。
6. **中文表达与隐私信任**：优化口语、专有名词和混合语言；明确音频保存、AI 处理、导出和删除规则。

## 4. 产品原则

1. 捕捉成功比转写成功重要。
2. 原始记录不可被 AI 覆盖；AI 内容必须可追溯、可重做。
3. 捕捉时不要求选项目、标签或模板，默认进入“收件箱”。
4. 用户停止录音后 1 秒内必须收到“已安全保存”的确定反馈。
5. 网络、模型和后台服务都不是捕捉成功的前置条件。
6. Agent 默认只建议，不替用户执行外部高风险操作。
7. 每张卡片只给一个主要继续入口，避免把灵感变成项目评审报告。
8. 先证明用户会持续捕捉和回看，再扩展会议、MCP、协作和复杂工作流。

## 5. 核心用户闭环

### 5.1 捕捉

- 从 App 首页、桌面/锁屏入口或系统快捷方式启动；
- 一次操作开始录音；
- 用户停止后，原始音频与捕捉元数据立即本地落盘；
- 清晰反馈“已保存”，用户可以立即离开。

### 5.2 异步整理

- 网络可用时上传并转写；
- AI 生成一句话标题、核心想法、待确认点和一个建议动作；
- 自动关联少量历史记忆；
- 整理失败可重试，不影响原始记录。

### 5.3 记忆卡

一张卡片优先展示：

- 一句话核心；
- 原始表达与音频；
- 捕捉时间、来源和可选地点；
- 1—3 条相关旧想法；
- 一个下一步：继续想、设提醒、转成行动或暂时归档。

不再把“可行性 high/medium/low”作为所有想法的必填结论。

### 5.4 主动复现

- 次日轻提醒：昨天这个想法是否值得继续？
- 每周回顾：本周反复出现的主题与互相关联的想法；
- 用户可以控制频率、静默时段和关闭复现；
- 每次复现都记录“有用 / 无关 / 稍后”，用于改进个性化。

## 6. MVP 范围

### 6.1 必须有

- 手机端一键录音与文字兜底；
- 本地音频/草稿保存和离线队列；
- 真实可用的中文 STT；
- 后端幂等创建记录；
- 异步 AI 整理状态：已捕捉、待同步、整理中、已整理、失败可重试；
- 记忆卡列表、详情、全文搜索；
- 时间、时区、入口来源，以及用户授权后的可选地点；
- 一种主动复现机制（建议先做每日或隔日回访）；
- 最小可用的真实认证、数据导出和账号删除；
- HTTPS/WSS、用户数据隔离和基础可观测性。

### 6.2 MVP 明确不做

- 多 Agent 自主编排；
- 让 Agent 决定是否保存记录；
- Notion、邮件等 MCP 执行；
- 企业协作和 Web Admin；
- 微信、QQ、手机号三套登录同时上线；
- 10K 并发和 99.9% SLA 的提前建设；
- 完整项目管理；
- 会议转写、长音频和内容创作模板大全。

## 7. 成功指标

### 7.1 北极星指标

**7 日有效复用率**：一条捕捉在 7 天内被用户回看、补充、继续追问、设置提醒、导出或标记“有用”的比例。

它同时约束三件事：用户愿意捕捉、系统整理有价值、旧想法确实能重新进入用户思考。

### 7.2 可靠性指标

- 从触发入口到开始录音：P50 < 1.5 秒；
- 停止录音到显示“已安全保存”：P95 < 1 秒；
- 本地捕捉成功率 ≥ 99.9%；
- 断网捕捉后恢复网络的最终同步率 ≥ 99%；
- 不允许因 STT/LLM 故障丢失原始记录；
- 崩溃无感率和无崩溃会话率达到内测发布门槛。

### 7.3 内测验证门槛

- 20—30 名种子用户连续使用 4 周；
- 至少 40% 的用户每周捕捉 3 条以上；
- 至少 30% 的捕捉产生有效复用行为；
- 至少 60% 的活跃用户认为“比给自己发消息/系统备忘录更不容易丢想法”；
- 复现提醒“有用”反馈明显高于“打扰”。

## 8. 当前实现评审

### 8.1 可保留的技术资产

- Flutter + Riverpod + GoRouter 客户端骨架；
- Go + Gin + PostgreSQL 后端；
- STT、Review、Embedding Provider 抽象；
- 原始输入与结构化数据分离的方向；
- pgvector 语义检索能力；
- 想法列表、搜索、标签和基础卡片；
- MCP 凭据隔离思路，作为后续能力保留。

### 8.2 必须重构

- 当前“在线录音 → 等 Agent → 用户确认 → 保存”改为“本地保存 → 服务端确定性保存 → 异步整理”；
- Agent 不再拥有创建记录的自主权；
- 捕捉 API、状态机、幂等键和失败重试；
- 真机 API 配置、HTTPS/WSS 和 WebSocket 鉴权；
- 真实认证与所有权校验；
- 数据模型补齐 captured_at、timezone、source、processing_status、audio_ref 和可选 context；
- 卡片从“标签/可行性/建议报告”改成“核心想法/情境/关联/一个下一步”；
- 录音生命周期、尾句确认、断线清理和后台状态处理。

### 8.3 暂时冻结

- Temporal 在单条捕捉热路径中的使用；
- ReAct 多工具循环；
- Notion/Email MCP UI；
- 当前“动态”执行日志页；
- 复杂项目隔离；
- 自动批准的 HITL；
- 当前未实际工作的每日聚合。

## 9. 关键风险

1. **同质化风险**：国内外产品已经覆盖语音记录、AI 整理、知识库、手表入口和 MCP；必须通过场景、可靠性和复现体验胜出。
2. **信任风险**：一次录音丢失可能导致用户永久流失。
3. **隐私风险**：语音、地点和长期画像高度敏感，必须默认最小采集、显式授权、可导出和可删除。
4. **AI 噪声风险**：每次都输出大量建议会让用户疲劳；整理需要短、准、可关闭。
5. **平台风险**：快捷入口、后台录音和系统限制在 Android/iOS 上差异很大，需要明确首发平台。
6. **范围风险**：继续同时建设 MCP、Temporal、会议、项目和多端，会再次推迟核心闭环。

## 10. 需要产品负责人拍板的三个问题

1. “双端”指 Android + iOS，还是手机 + 桌面？V2 建议先确定一个主捕捉端和一个回顾端。
2. 首发用户是否以中文创造型个人用户为主？如果是，应放弃泛人群 PRD。
3. 原始音频默认保留多久？建议默认保留且允许用户选择仅本地、云端保留周期或立即删除。
